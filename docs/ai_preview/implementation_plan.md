# 本地资料库实施规划

## 1. 当前阶段

先完成本地资料库，再开始 Prompt 工程和生成质量验收。本文中的“资料库”指由 Markdown
和 JSON 文件组成的本地资料集合，当前不建设网站，也暂不确定是否需要数据库服务。

本阶段只确定资料边界、文件类型和大致目录，不提前固定解析工具、同步流程、JSON Schema
或 Prompt 上下文格式。

## 2. 大致文件框架

```text
data/ai_preview/
├── institutions/
│   └── <院系名称>.md
├── automatic/
│   ├── tournaments/
│   │   └── <赛事标识>.json
│   └── games/
│       └── <比赛标识>.json
├── corpus/
│   └── <前瞻文章>.md
├── writing_rules.md
└── runs/
    └── <生成记录>/...
```

这是候选框架，不是最终接口。索引文件、运行记录的内容以及是否需要额外清单，等实际维护
资料时再决定。

## 3. 文件类型与内容边界

### 3.1 院系资料：Markdown

- 每个院系一个文档，院系清单以现有 `teams.json` 为准。
- 文档包含男足、女足、五人制三支队伍的描述；没有对应队伍时写“无”。
- 文档包含 25-26 赛季该院系全部报名球员的描述。
- 每支球队和每名球员均只有一段人工维护的描述字符串。
- 球员在院系内以姓名识别，完整定位为“院系 + 姓名”；院系内重名交由人工处理。
- 描述可以包含风格、年级、位置、伤病等人工信息，不重复系统能够取得的比赛统计。

院系文档的具体标题层级和解析约定，在制作首批样例后再确定。

### 3.2 自动资料：JSON

用于保存系统能够取得的赛事、比赛、比分、事件、排名和球员比赛数据。只保留前瞻可能使用
的字段，不保存手机号、证件信息或完整接口响应。

赛事与比赛是否分别保存、往届数据是否冻结、当前数据何时刷新以及汇总数据是否现场计算，
均在查看实际接口数据后确定。JSON 的字段和版本格式也不在当前阶段锁定。

### 3.3 语料和规则：Markdown

- 每篇优秀前瞻保存为独立文档。
- 暂不按写作风格分类。
- `writing_rules.md` 用于人工整理通用正文要求、标题要求和禁用表达。
- 是否建立 JSON 索引以及索引字段，等语料数量和使用方式明确后决定。

## 4. 实施顺序

### 阶段一：搭建并填充本地资料库

1. 确认目录和院系文档样例。
2. 根据 `teams.json` 建立院系文档骨架。
3. 整理 25-26 赛季报名球员并归入院系文档。
4. 逐步人工填写球队和球员描述。
5. 准备一批赛事、比赛和球员自动数据样例。
6. 收集优秀前瞻并初步整理通用规则。
7. 根据实际资料修订文件结构，完成资料库阶段检查。

阶段检查重点是：现有球队和报名球员能够被表达和定位；人工内容与自动内容边界清楚；
若干真实比赛所需资料能够从本地文件中找到。暂不设置精确覆盖率或字段完整度指标。

### 阶段二：Prompt 工程和验收

资料库结构基本稳定后，再确定 Prompt 的组织形式、上下文选择方式和输出格式。使用约
5-10 场比赛进行本地试写和人工验收，记录问题后迭代。

### 阶段三：网站接入

本地资料维护和生成效果得到初步验证后，再讨论网站中的维护入口、生成入口和人工发布流程。

## 5. 当前暂不确定的事项

- 自动数据的获取、刷新、缓存和历史快照策略；
- 自动 JSON 的具体字段、粒度和版本格式；
- Markdown 的最终标题模板与解析方式；
- 检查、导入和上下文组装工具的具体实现；
- Prompt 的消息结构、示例选择、事实引用和输出 Schema；
- 生成记录的目录与保存内容；
- 未来是否导入 SQLite、网站数据库或继续直接读取文件。

这些事项在资料库搭建过程中根据真实数据和维护体验逐项确定。

## P0：确认本地资料库框架

- [ ] 用少量院系、球队、球员和比赛数据制作文件样例。
- [ ] 确认 Markdown 与 JSON 的大致目录和内容边界。

阶段判断：文件结构可以表达人工描述、自动比赛数据和前瞻语料；具体 Schema 暂不锁定。

## P1：建立人工球队和球员资料

- [ ] 以 `teams.json` 为准建立每个院系的 Markdown 文档。
- [ ] 每个院系保留男足、女足、五人制球队描述。
- [ ] 整理 25-26 赛季全部报名球员，并按“院系 + 姓名”定位。
- [ ] 记录院系映射、同院系重名和名单异常，交由人工处理。
- [ ] 逐步填写每支球队和每名球员的一段式描述。

阶段判断：抽查球队和球员能够在文档中定位，人工资料可以直接维护；暂不设置精确覆盖率。

## P2：准备自动资料和语料

- [ ] 选取若干赛事与比赛，保存可供前瞻使用的 JSON 数据样例。
- [ ] 区分人工描述与系统可获取的赛果、排名、事件和球员统计。
- [ ] 排除敏感、无关字段和完整原始接口响应。
- [ ] 收集一批优秀前瞻 Markdown 文档，暂不按写作风格分类。
- [ ] 初步整理通用正文要求、标题要求和禁用表达。
- [ ] 根据真实数据决定后续快照、刷新、索引和检查方案。

阶段判断：若干真实比赛需要的主要资料可从本地文件取得，缺项和未决问题已被记录。

## P3：资料库阶段检查

- [ ] 检查院系、球队和球员的基本覆盖与定位问题。

- [ ] 评估 Markdown 是否便于人工长期编辑、JSON 是否便于程序读取。
- [ ] 根据维护体验确定下一阶段需要的最小工具。

完成本阶段后，再开始确定 Prompt 的具体组织方式。

- [ ] 建立首版 Prompt；暂不区分写作风格。
- [ ] 制作约 5-10 场的评测集。
- [ ] 人工记录事实错误、资料使用、结构、可读性和修改成本。
- [ ] 根据试写结果迭代 Prompt，并逐步明确后续验收标准。

阶段判断：首轮以发现问题为主，不设置精确分数和通过比例。

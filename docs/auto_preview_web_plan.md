# Auto Preview 网站实施计划

## 总体顺序

先完成全部后端能力，并通过 FastAPI `/docs`、HTTP 请求和自动化测试手动跑通完整流程；后端验收后才开始前端。PostgreSQL 是唯一业务数据源，`var/artifacts/` 只保存可重建文章产物，现有 CLI 暂时保持不变。

## 第一阶段：后端基础

- 建立 FastAPI、Docker PostgreSQL、Alembic 和单 worker。
- 建立用户、前瞻批次、比赛任务、天气、编辑人员、文章版本、微信草稿和后台任务模型。
- 提供初始化命令创建首个管理员。
- 使用安全 Cookie 会话，实现登录、退出、修改密码和管理员创建账号。
- 提供 `/health` 和 `/docs`，本机默认只监听 `127.0.0.1`。

## 第二阶段：前瞻 API

- 创建“日期 × 赛事”批次并异步生成数据。
- 调用现有 THUFootball 查询和 `PreviewSourceBuilder`，直接保存数据库。
- 重新查询按 `game_id` 更新自动数据，但保留认领、署名和正文。
- 提供标题、天气、编辑/责编/审核和封面的读取与修改 API。
- 提供比赛认领、管理员转交、多人署名修改和正文手动保存 API。
- 正文保存使用版本号，冲突返回 HTTP 409。

## 第三阶段：文章与微信 API

- 从数据库组装 `PreviewSourceData`，复用 `PreviewService.render()`。
- 内容不完整时允许生成带占位提示的预览版本。
- 标题、天气、人员、正文和署名完整后，文章版本才标记为可发布。
- 提供文章 HTML、封面和版本信息读取 API。
- 管理员可选择并排序 1–8 篇最新完整文章，创建微信公众号草稿。
- 复用现有内容指纹进行幂等保护；保存 `media_id` 和文章版本关系。
- 微信真实写入必须显式传入确认字段，测试默认使用假服务。

## 第四阶段：手动跑通 API

按以下顺序通过 `/docs` 或 HTTP 客户端验证：

1. 初始化管理员并登录。
2. 创建写作者账号。
3. 创建日期与赛事批次，轮询后台任务直到数据生成完成。
4. 查看比赛任务和自动查询数据。
5. 修改标题、天气、人员和封面。
6. 使用写作者账号认领比赛并保存多段正文。
7. 验证重复认领、越权编辑和旧版本覆盖均被拒绝。
8. 在内容不完整时生成预览，并验证微信草稿接口被阻止。
9. 补齐全部内容，生成新的可发布文章版本。
10. 使用假微信服务验证 1–8 篇排序、指纹和重复提交。
11. 最后显式执行一次真实微信公众号草稿创建并核对 `media_id`。

同时提供可重复执行的 API smoke test，使这条流程不依赖人工逐项点击。

## 第五阶段：前端

后端验收完成后再开发 React 网站：

- 登录与账号管理。
- 批次列表和任务进度。
- 标题、天气、人员和封面编辑。
- 单场比赛认领与正文手动保存。
- 文章预览与完整性提示。
- 1–8 篇文章选择、排序和微信草稿确认。

## 验收标准

- 全部后端流程在没有前端的情况下可通过 `/docs` 完成。
- PostgreSQL 是唯一可编辑数据源，不与 `runs/` 双向同步。
- 后台任务重试不会重复创建批次、比赛或微信草稿。
- 权限、认领并发、正文版本冲突和发布完整性均有 API 测试。
- 现有 CLI 和原有测试在网站后端建设期间保持原有行为。

## 实施顺序说明

该计划描述完整的 Auto Preview 网站，包括管理员与用户能力。实际实施时按以下顺序推进：

1. 先完成管理员后端闭环。
2. 再增加写作者账号、比赛认领、权限和版本冲突能力。
3. 全部后端 API 验收后再开发前端。

# 自动化比赛前瞻工具：原子能力测试计划

## 1. 文档目的

本文档用于指导自动化比赛前瞻管线的前置能力验证。当前阶段只设计测试，不实现测试代码、不访问真实接口，也不创建公众号草稿。

THUFootball 侧的接口输入依据见 [THUFootball 比赛 API 使用说明](./thufootball_api.md)。

计划覆盖两条能力链：

1. 从 THUFootball 获取指定自然日的比赛，并生成两队近期战绩、历史交手等结构化数据。
2. 读取已发表公众号前瞻的正文 HTML，形成可复用模板，填充新内容、处理媒体资源，并将文章提交至公众号草稿箱。

当前阶段的目标不是尽快跑通一次端到端流程，而是回答以下问题：

- 每个底层能力是否独立成立？
- 输入、输出和错误语义是否稳定、可替换？
- 一项能力失败时，能否精确定位到日期、接口、数据规则、HTML、媒体或公众号权限？
- 在开始搭建管线前，是否已经有足够的契约和证据避免把未知问题带入编排层？

## 2. 范围与非目标

### 2.1 本阶段范围

- 定义领域对象和外部系统适配器的边界。
- 设计纯函数测试、协议契约测试、只读能力探针和受控写入探针。
- 设计固定样本、预期结果、错误分类、验收闸门和执行顺序。
- 明确 THUFootball 历史数据的实际覆盖范围。
- 明确公众号文章源码读取、样式复用、图片处理和草稿写入的必要能力。
- 为后续加入新的赛事数据源、模板版本或发布渠道保留接口。

### 2.2 本阶段非目标

- 不实现测试、爬虫、数据客户端、模板引擎或草稿客户端。
- 不使用真实账号、密钥、Cookie 或文章链接进行测试。
- 不自动发布公众号文章；最终自动化边界只到“草稿箱”。
- 不评价前瞻文案的文学质量、预测准确率或人工编辑质量。
- 不在尚未证实底层能力前设计完整调度、重试队列和生产部署。

## 3. 需要先固定的业务语义

以下语义直接影响测试预期。可以先采用本文默认值，之后通过配置调整，不应把它们散落在测试代码中。

| 语义 | 默认设计 | 说明 |
| --- | --- | --- |
| 业务时区 | `Asia/Shanghai` | “某一天”按该时区的自然日解释 |
| 日期区间 | `[00:00:00, 次日 00:00:00)` | 使用左闭右开区间，避免依赖 `23:59:59` 精度 |
| 历史比赛 | 开球时间严格早于目标比赛 | 不纳入当前比赛和未来比赛 |
| 近期战绩数量 | 可配置 `N`，测试默认 `5` | 截断前先按时间倒序排列 |
| 历史交手身份 | 使用稳定队伍 ID，不使用队名 | 队名变化不应破坏匹配 |
| 未完赛比赛 | 不进入胜平负及进失球统计 | 可保留在赛程信息中，但必须标明状态 |
| 历史数据范围 | 默认标注为“同赛事内历史” | 现有说明中的 `GetTournInfo` 不能自然证明跨赛事、跨赛季全历史 |
| 公众号源码 | 指可复用的正文 HTML 和必要元数据 | 不等同于保存整页 HTML、脚本或登录态 |
| 模板动态区 | 使用显式占位符/区块定义 | 不依赖每次运行时猜测哪些文字需要替换 |
| 自动化终点 | 成功创建草稿并返回草稿标识 | 发布动作不在允许调用集合内 |

如果后续要求“全校史交锋”而不是“同赛事交锋”，必须新增数据发现能力和对应适配器；不能把同赛事数据静默描述成全历史。

## 4. 建议的能力边界

后续实现应面向领域接口，而不是让管线直接拼接 HTTP、操作 HTML 或调用公众号接口。

```text
TargetDate
  -> THUFootballGateway
  -> 上游编排/写作流程
  -> PreviewSourceData JSON

PublishedArticleRef
  -> ArticleSourceReader
  -> HtmlNormalizer
  -> PreviewTemplate

PreviewSourceData JSON
  -> StrictPreviewDecoder
  -> PreviewSourceData
  -> PreviewTemplate.render(source)
  -> RenderedArticle
  -> MediaPublisher
  -> DraftPayloadBuilder
  -> WechatDraftGateway
  -> DraftReceipt
```

建议最小领域对象：

| 对象 | 最小职责 |
| --- | --- |
| `TargetDate` | 日期、业务时区及对应时间区间 |
| `GameRef` | 比赛 ID、开球时间、赛事 ID、主客队 ID |
| `GameSnapshot` | 单场比赛的展示信息和比赛状态 |
| `TeamForm` | 某队近期比赛及聚合结果 |
| `HeadToHead` | 两队历史交手及数据覆盖范围说明 |
| `PreviewSourceData` | 多场前瞻的干净事实、结构化赛果和纯文本写作内容 |
| `PreviewColumnConfig` | 嵌套在 `PreviewSourceData.column` 中的男足、女足或五人制栏目身份 |
| `ArticleSource` | 正文 HTML、标题、来源 URL、媒体引用清单 |
| `PreviewTemplate` | 只接受类型化前瞻源数据的静态布局和安全模板 |
| `RenderedArticle` | 已填充、已清理但尚未上传媒体的正文 |
| `DraftPayload` | 符合草稿适配器输入约束的文章数据 |
| `DraftReceipt` | 草稿标识、内容指纹、创建时间和追踪 ID |

外部依赖应通过以下端口隔离：

- `Clock`：提供可冻结的当前时间。
- `THUFootballGateway`：只负责请求和响应映射，不负责近期战绩计算。
- `ArticleSourceReader`：只负责取得来源，不负责模板推断。
- `HtmlNormalizer`：只负责确定性清理和标准化。
- `PreviewTemplate`：直接接受 `PreviewSourceData` 与栏目配置，不读取旧展示 DTO。
- `MediaPublisher`：负责图片上传及 URL 替换。
- `WechatDraftGateway`：只负责草稿操作，不暴露发布操作。

## 5. 原子测试设计规范

### 5.1 原子性的定义

每个测试只验证一个可命名行为：一个输入变化、一个被测能力、一个主要可观察结果。

示例：

- “目标比赛作为主队时判定为胜”与“作为客队时判定为胜”是两个测试。
- “HTML 清除 `script`”与“HTML 保留允许的行内样式”是两个测试。
- “令牌过期后刷新”与“鉴权错误不重试”是两个测试。

单个测试可以有多个机械性断言，但它们必须共同证明同一个行为，不能把请求、统计、渲染、上传和草稿创建塞进同一个测试。

### 5.2 测试记录模板

每项测试实现时均应记录：

```text
ID:
能力问题:
层级: L0/L1/L2/L3
Given: 最小输入或前置状态
When: 唯一动作
Then: 唯一主要结果
禁止依赖:
证据: 返回值 / 请求快照 / HTML 快照 / 图片差异 / 草稿标识
失败分类:
```

### 5.3 测试层级

| 层级 | 类型 | 外部副作用 | 用途 |
| --- | --- | --- | --- |
| `L0` | 纯函数/固定样本测试 | 无网络、无文件外写 | 验证日期、筛选、统计、HTML 转换和数据映射 |
| `L1` | 适配器协议测试 | 使用本地桩或录制样本 | 验证请求参数、响应解析、超时、错误映射 |
| `L2` | 真实只读能力探针 | 仅允许读取 | 验证账号权限、真实字段、来源可访问性和语义假设 |
| `L3` | 真实受控写入探针 | 只允许测试素材和草稿 | 验证媒体上传、草稿新增/读取/删除；严禁发布 |

`L0` 和 `L1` 应是常规回归测试。`L2`、`L3` 需要显式开关、独立测试账号和运行记录，不应在每次本地测试时自动执行。

当前目录共定义 137 项测试：`L0` 92 项、`L1` 34 项、`L2` 6 项、`L3` 5 项。后续新增测试时应保留唯一 ID，并归入明确闸门。

## 6. 固定样本设计

测试样本是能力契约的一部分。样本应脱敏、最小化、可读，并与真实适配器返回值分离。

建议目录：

```text
tests/
  fixtures/
    thufootball/
      current_games/
      game_info/
      tournament_info/
      errors/
    article_source/
      raw/
      normalized/
      templates/
      rendered/
    wechat_api/
      auth/
      media/
      draft/
  unit/
  contract/
  probes/
```

最低样本集：

- 位于当天起点、当天中间、次日零点的三场比赛。
- 目标队分别作为主队和客队的已完赛比赛。
- 平局、未完赛、延期、缺失比分和异常比分样本。
- 正反主客场的两队交锋、同名不同 ID、改名同 ID 样本。
- 空比赛日、空历史、重复比赛 ID、乱序比赛列表。
- 一份最小公众号正文、一份复杂排版正文、一份含图片/链接正文。
- 含脚本、事件属性、不允许标签的恶意 HTML 样本。
- 正常、鉴权失败、限流、超时、字段缺失的 API 响应样本。

原始样本一经作为契约使用就不应原地修改；字段演进时新增版本，例如 `game_info_v2.json`，并明确兼容预期。

## 9. 公众号来源、模板与排版原子能力测试目录

### 9.1 已发表文章来源读取

来源适配器只处理公开或已授权访问的文章。遇到验证页、访问限制或权限问题时，应返回明确错误或切换到预先设计的合规适配器，不设计绕过访问控制的逻辑。

| ID | 层级 | 原子能力 | 最小输入/动作 | 通过标准 |
| --- | --- | --- | --- | --- |
| `SRC-FETCH-001` | L1 | 请求公开文章 URL | 桩返回正常 HTML | 产出原始文档和最终 URL |

## 12. 错误模型与可观测性

建议统一错误分类：

```text
ConfigurationError
AuthenticationError
PermissionError
Timeout
RateLimited
InvalidResponse
SchemaError
DataConflict
InsufficientHistoryCoverage
SourceAccessBlocked
UnsafeHtml
TemplateContractError
PreviewValidationError
MediaUploadError
DraftValidationError
DraftWriteError
```

每个错误至少包含：

- 稳定错误类型和阶段名。
- `run_id`。
- 相关业务标识，例如比赛 ID、文章 URL 的脱敏形式或图片序号。
- 可重试性：`retryable: true/false`。
- 不含密钥、令牌、Cookie 和完整敏感响应的安全摘要。

原子测试需分别验证错误分类，不用“抛出任意异常”作为通过标准。

最小运行记录应包含：

- 目标日期与时区。
- 找到的比赛 ID 列表。
- 每场使用的数据覆盖范围及缺失项。
- 来源文章指纹、模板版本、优化规则版本。
- 媒体任务数量与成功数量，不记录凭据。
- 草稿内容指纹和草稿标识。
- 每阶段开始、结束、耗时和结果。

## 13. 能力闸门与执行顺序

### Gate 0：语义和契约冻结

完成条件：

- 第 3 节的默认语义已经确认或改为明确配置。
- 领域对象和适配器接口已形成版本化契约。
- 明确“历史交手”的覆盖口径。
- 明确允许的公众号文章来源与自动访问方式。

### Gate 1：离线原子能力成立

执行范围：全部 `L0`。

完成条件：

- 日期边界、球队身份、历史筛选、主客场视角和统计全部通过。
- HTML 清理、样式保留、模板填充和指纹全部通过。
- 草稿载荷在无网络条件下可以完整校验。
- 测试不依赖执行顺序、当前日期或真实密钥。

### Gate 2：协议适配能力成立

执行范围：全部 `L1`。

完成条件：

- THUFootball、来源读取和公众号接口的请求/响应契约通过。
- 超时、鉴权、限流、异常响应均映射为稳定错误。
- 相邻接缝测试通过。
- 没有真实外部写入。

### Gate 3：真实只读能力成立

执行范围：全部 `L2`，使用专用配置手动触发。

完成条件：

- THUFootball 凭据、日期和字段语义得到证实。
- 历史覆盖口径得到事实确认；若不足，已有新数据策略或明确降级文案。
- 授权公众号文章来源能够稳定取得正文，或已有合规且可自动化的来源适配器。
- 公众号账号具备后续媒体和草稿能力所需权限。

### Gate 4：受控草稿写入成立

执行范围：全部 `L3`，使用测试账号/测试素材手动触发。

完成条件：

- 正文图片、封面、草稿新增和草稿读取分别通过。
- 测试草稿可按本次 `run_id` 清理。
- 重复保护生效。
- 代码和账号权限范围内均没有自动发布路径。

### Gate 5：允许开始搭建管线

只有 Gate 0 至 Gate 4 全部完成，才进入管线实现。若某个能力有明确的非关键降级方案，必须在例外清单中记录：影响范围、用户可见表现、监控方法和后续解决条件。

## 14. 后续管线阶段的实施顺序

本节只规定未来顺序，不属于当前实现任务。

1. 建立领域对象、固定时钟、错误模型和固定样本。
2. 实现并通过 THUFootball 的 `L0` 筛选/统计测试。
3. 实现并通过 THUFootball 的 `L1` 适配器测试。
4. 实现来源提取、HTML 清理和模板契约的 `L0/L1` 测试。
5. 实现媒体与草稿载荷的 `L0/L1` 测试。
6. 依次执行 `L2` 只读探针，修正真实字段和权限假设。
7. 依次执行 `L3` 写入探针并确认清理策略。
8. 连接相邻接缝；每次只增加一个边界。
9. 最后编写按日期编排的管线、运行状态存储和人工复核入口。

## 15. 扩展性要求

- 新数据源必须实现相同的比赛领域契约，不能让模板依赖 THUFootball 原始字段。
- 新模板只能通过版本、占位符契约和规则集扩展，不能修改旧模板黄金样本。
- 新公众号账号或其他渠道应实现新的草稿网关，不改变 `RenderedArticle`。
- 所有时间逻辑必须依赖 `Clock` 和显式时区。
- 所有网络适配器必须支持桩替换，纯函数测试不得读取网络。
- 每发现一个线上字段变体，先新增最小固定样本和原子测试，再修改适配器。
- 若将来加入大模型撰写，只把它作为 `EditorialInputProvider`；排版、媒体和草稿能力不得依赖模型输出格式。模型输出需另有结构化 schema、事实引用和人工审核测试。

## 16. 主要风险及其判定点

| 风险 | 不应如何掩盖 | 对应判定点 |
| --- | --- | --- |
| API 时间无时区 | 不用字符串比较碰运气 | `CORE-TIME-*`、`THU-LIST-009` |
| 同赛事历史被误称为全部历史 | 不用模糊文案默认扩大范围 | `THU-COVERAGE-*` |
| 队名变更或重名 | 不按展示名关联 | `THU-IDENTITY-*` |
| 公众号来源触发限制 | 不把验证页保存为模板，不绕过访问控制 | `SRC-FETCH-003/005/006` |
| 原页面样式依赖运行时 CSS | 不仅比较 HTML 字符串 | `HTML-STYLE-*`、`VIEW-REGION-*` |
| 外部图片不能直接用于草稿 | 不在提交时临时猜测 | `WX-MEDIA-*`、`WX-PAYLOAD-006` |
| 重试产生重复草稿 | 不把新增草稿当幂等读取重试 | `WX-DRAFT-004/005` |
| 凭据泄漏 | 不保存完整请求/响应调试包 | `CORE-SECRET-001` |
| 写入测试误发布 | 不提供发布接口 | `WX-DRAFT-006` |
